# 产品技术决策

下列是实现选择及可检查的依据。默认 `s_team / t1 / g2` 由负责人指定；本次验收不比较推荐质量或组件收益，各选择未经实验验证。

| 决策 | 考虑的方案 | 采用方案与原因 | 依据及限制 |
|---|---|---|---|
| 任务执行结构 | 通用自主 Agent；按产品阶段限定的 harness | harness 只负责工具执行、校验、状态和追踪；推荐、plan、对话分别开放所需工具，使页面动作有稳定接口。 | `backend/harness/loop.py`、`tools.py` 及 mock 干预测试；不是通用任务规划系统。 |
| 结构化结果 | 解析自由文本；JSON 输出模式；提交工具 | 新策略用 `submit_*` 工具，推理字段在答案前，Pydantic 和业务校验失败后返回工具结果，允许限次修正。团队 `s_team` 保留原 JSON 模式。 | `recommend/strategies.py`、`tutor/plan.py`、`qa/answer.py`；通过校验仅表示结构和约束满足。 |
| 推荐约束 | 全交给模型；代码先过滤 | 代码执行实际人数、独立主持和专用道具约束。团队标签权重保留在 `s_team`，其他新策略不添加手写领域评分。 | `recommend/common.py`、`s_team.py` 及团队基线回归；推荐理由仍可能不贴合场景。 |
| 带玩流程 | 每一步都由模型决定；lesson plan 加代码状态 | 默认 `t1` 先产生计划，harness 持有阶段、索引、名单和分数；下一步与跳转无需模型，明确区分内容生成与状态修改。 | `tutor/plan.py`、`state.py`、`session.py`；mock 可验证推进与恢复，不能证明教学效果。 |
| 来源表达 | 不区分来源；每句话提供统一标签 | 使用 `[[dataset]]`、`[[rulebook]]`、`[[general]]` 和搜索路径中的 `[[web]]`；界面显示徽标及网页链接，让使用者看到来源类别。默认 `g2`，其他策略实现保留。 | `qa/answer.py`、`frontend/shared/play.js`；标签是声明，不能替代事实核对。 |
| 联网搜索 | 厂商内置搜索；harness 的搜索和取网页工具 | harness 提供 `web_search`、`fetch_page`、缓存检索；来源和工具事件可持久化，不依赖某家模型的专有搜索格式。默认关闭，只在缺少规则书时补充。 | `tutor/web.py`、`tools.py`；本次只用 mock 搜索验证流程，真实接口未测试。 |
| 技术栈 | 引入前端框架、向量库或通用 Agent 框架；沿用团队栈 | 沿用 FastAPI、Pydantic、SQLite、原生 HTML/CSS/JS，增加兼容接口客户端、Jinja、BM25；普通 pip 安装即可启动。 | `requirements.txt` 与冷启动记录；不需要前端构建、Docker 或独立数据库服务。 |
| 本地使用 | 账号部署；本机直接打开 | 本次只交付本地使用，保留模型设置，默认监听 `127.0.0.1:8001`，无需账号。 | 负责人当前要求、`start.py`、README；多人部署不在本次交付和验收范围。 |

`tests/` 中的自动检查和 `docs/coldstart.md` 中的浏览器实测分别证明接口行为和安装后的页面流程。mock 的固定文本不能作为实际模型能力、规则忠实度或搜索可用性的证明。
